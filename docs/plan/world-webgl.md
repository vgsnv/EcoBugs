# План перехода чашки на WebGL2

Дата: 2026-10-03. Основа сравнения: коммит `cefa392`. Статус: первоначальный план переноса только изображения; заменён [планом нового GPU-движка](world-gpu.md). Не использовать ограничения этого документа на неизменность алгоритмов и формата сохранений как требования к новой версии. Пользователь разрешил пересматривать реализацию ради соответствия спецификации и лучшей работы; две версии после выбора не поддерживаются.

## Цель и принятые решения

Перенести всю отрисовку мира чашки на WebGL2: местность, среду, свет, минерал, источники, перегородки, стенки, диагностические обозначения и миникарту. Получить единый управляемый GPU-рендер и запас для развития визуальных эффектов.

- Изменения только в `world/` и `docs/`.
- WebGL2 обязателен. Запасного рендерера Canvas 2D и поддержки WebGL1 в конечной версии нет.
- Без новых библиотек: TypeScript, WebGL2, собственные GLSL ES 3.00 шейдеры и небольшой слой управления ресурсами.
- Мир остаётся плоским; камера ортографическая. Переход не требует 3D-сцены, перспективы, атмосферы или модели ветра.
- Физика, Worker, метрические единицы, сиды и формат сохранений остаются прежними. GPU получает законченные состояния и никогда не записывает результат в физические массивы.
- HTML-панели, управление и доступные подписи остаются в DOM. Canvas 2D допустим для однократной подготовки атласа текста/изображений, но не для сборки кадра чашки.
- Временный старый рендер разрешён только для разработки и сравнения. После завершения миграции он удаляется.

Переход и улучшение художественного результата — две последовательные задачи. Сначала воспроизводим текущую картинку и поведение, затем меняем эффекты. Ускорение физики и изменение профиля вулканического выброса в этот план не входят.

## Исходная архитектура и точки переноса

`world/src/app/render.ts` сейчас объединяет камеру, подготовку местности, кэш плиток и сборку нескольких Canvas-слоёв. `WaterFlowShader` использует отдельный контекст WebGL1, после чего его холст копируется в Canvas 2D. `main.ts` передаёт отдельные часы `animTime`, `flowStep` и шаг физики; миникарта рисуется отдельным методом. `rulers.ts` использует пути и текст Canvas 2D.

| Текущий участок | Целевое решение |
| --- | --- |
| `drawTerrain`, `base`, `tiles`, `terrainSampler` | GPU-местность из карт полей и статических данных; обновление изменившихся участков |
| `spots`, `shade`, размытие света | Маска света и небольшие GPU-проходы размытия |
| `drawGlints`, `WaterFlowShader`, `waterMask` | Вода в основном WebGL2-контексте, общая маска местности и карта физической скорости |
| `mineralCanvas`, `murkCanvas`, `lightMurkCanvas` | Карта плотности, визуальное сглаживание, цвет и ослабление света на GPU |
| `drawGrains`, `drawSpring`, `drawFunnels`, `drawEruptions` | Группы экземпляров спрайтов и процедурных фигур |
| `drawWalls`, `parts`, `edges`, тень чашки | Геометрия/аналитические маски и отдельный проход рамки |
| `drawProcesses`, указатель пробы | GPU-геометрия линий и диагностических знаков |
| `CoordinateRulers` | GPU-линии и атлас подписей |
| `drawMinimap` | Та же сцена с другой камерой и отдельной целью вывода |

## Целевая организация

Оставить `WorldRenderer` фасадом для приложения, сохранив существующие публичные операции камеры, загрузки мира, рисования, пробы и миникарты. Перед выделением модулей перечислить фактические вызовы из `main.ts`, чтобы не потерять операции управления.

Предварительное разбиение в `world/src/app/gpu/`:

- `device.ts`: создание контекста, возможности, потеря/восстановление, освобождение ресурсов.
- `resources.ts`: программы, текстуры, framebuffer, буферы, VAO; владельцы и размеры.
- `camera.ts`: преобразования мира, CSS-пикселей и пикселей устройства, область видимости.
- `world-fields.ts`: подготовка и обновление карт из законченного состояния мира.
- `terrain.ts`, `medium.ts`, `lighting.ts`: проходы поверхности, среды и света.
- `effects.ts`: вулканы, воронки, частицы и вспышки.
- `overlays.ts`: процессы, проба, линейки, рамка миникарты.
- `shaders/`: небольшие GLSL-модули или строки, совместимые с существующей сборкой Vite.

Это специализированный рендерер мира, не универсальный игровой движок. Не вводить абстракции сцены, материалы и граф проходов до появления реальной необходимости.

### Данные и GPU-ресурсы

| Данные | Предлагаемый формат и семантика | Когда обновлять |
| --- | --- | --- |
| Местность/залежи | Числовые текстуры уровня и плотности; точные формат и число каналов выбрать после инвентаризации диапазонов | При смене мира и изменениях соответствующих полей |
| Минерал среды | `R32F`, чтение через `texelFetch`; визуальное сглаживание отдельно | При новой версии минерала, с ограничением частоты показа |
| Скорость | `RG32F`, компоненты в мм/с; ручная интерполяция | При изменении составляющих `flowAt`, а не просто при панорамировании |
| Препятствия/форма чашки | Аналитическая форма плюс дискретная маска, `R8` либо целочисленный аналог | При изменении геометрии |
| Свет и промежуточные изображения | `RGBA8`, разрешение по задаче | По времени света и изменениям среды |
| Рисунок ряби, частицы, подписи | Атласы `RGBA8` | Инициализация/изменение набора подписей |

Не предполагать доступность линейной фильтрации 32-битных float-текстур: базовый путь использует ближайшее чтение и ручную интерполяцию в шейдере. Не требовать float-framebuffer и расширения для рендера в них: числовые карты служат входными данными, базовые промежуточные цели — `RGBA8`. Это один рендер, а не разные режимы качества по наличию расширений.

Текстуры выделять при смене размеров, обновлять через `texSubImage2D`. Начать с полного обновления небольших числовых карт; частичные загрузки добавить там, где измерения подтверждают пользу. Проверить пределы текстур устройства; для больших миров предусмотреть разбиение на страницы или текстурные массивы, не уменьшать физический мир ради лимита GPU.

Версии полей описать явно. `mineral.version` недостаточно для всех данных: солнечная составляющая скорости зависит от времени, местность и сопротивление имеют свои изменения. Статические и динамические данные разделить; камера меняет uniforms, а не заставляет собирать всю карту мира заново.

### Время, маски и смешивание

Сохранить различие между завершённым `world.step`, временем показа `flowStep` и декоративным `animTime`. Перенос среды должен быть привязан к модельным секундам. На паузе эффекты стоят; движение камеры работает. При загрузке, смене сида и скачке времени сбрасываются визуальные накопители.

Единая маска чашки, суши, перегородок и отверстий источников используется всеми нужными проходами. Интерполяция скорости не должна создавать движение сквозь стену: учитывать маску соседних клеток и нормализовать допустимые веса. Сглаживание плотности также не должно переносить цвет через непроницаемую перегородку.

Зафиксировать один способ работы с альфой, предпочтительно premultiplied alpha для промежуточных изображений. Поведение нынешних `multiply`, `screen`, `destination-in` и `destination-out` воспроизвести явными формулами и масками. Не менять одновременно гамму/цветовое пространство и палитру: сначала проверить соответствие существующему изображению.

## Этап 0. База сравнения и карта требований

**Работа:** зафиксировать состояния мира и кадры на `cefa392`: молодой мир, первое извержение, зрелый мир с воронками, состояние после изменения местности. Добавить круг, прямоугольник, перегородки и узкий проход. Использовать одинаковые сохранения, шаг, камеру, разрешение и DPR при сравнении.

Снять базовые показатели: CPU-подготовка кадра, загрузка полей, интервалы кадров p50/p95/p99, пропуски кадров, задержки управления, оценка памяти. Проверить всю чашку и крупный масштаб, паузу, ×1 и ×10; более высокие скорости использовать для проверки частоты обновлений. Зафиксировать браузер, устройство и размеры холста.

**Результат:** отчёт в `docs/reports/`, таблица сцен и список функций, которые должен сохранить новый рендер. Наблюдение «60 FPS» само по себе не является доказательством ускорения.

**Приёмка:** контрольные состояния можно воспроизвести, понятны размер физических карт и их источники изменений. Измерения выполняются при реализации, не выдаются за уже проведённые в этом плане.

## Этап 1. Контекст, камера и жизненный цикл

**Работа:** создать WebGL2-контекст, минимальный полноэкранный проход, устройство ресурсов и общую камеру. Настроить resize, DPR, панорамирование, увеличение около указателя и вписывание чашки. Сохранить фасад `WorldRenderer`.

Canvas, уже получивший контекст `2d`, нельзя использовать как WebGL2-холст. На время сравнения использовать отдельные холсты или выбор реализации до создания контекста; переключение не должно перезапускать физику. Старый вариант не включается автоматически при ошибке WebGL.

При отсутствии WebGL2 показать DOM-сообщение с причиной и остановить запуск визуальной чашки без пустого экрана. При потере контекста остановить отправку GPU-команд, сохранить текущий мир и сообщить о восстановлении. Пересоздать программы и ресурсы из последнего законченного состояния, вернуть камеру и пользовательскую паузу. Определить поведение симуляции на время восстановления: запросить паузу и возобновить только если она работала до потери и пользователь не изменил это решение.

**Приёмка:** геометрия круга/прямоугольника совпадает; изменение размера и координаты указателя правильны при DPR 1 и 2. Ошибка создания и искусственная потеря контекста не теряют мир и не оставляют бесконечный цикл ошибок.

## Этап 2. Местность, перегородки и чашка

**Работа:** перенести семантику `terrainSampler`, палитру, залежи, берег и переходы вода–отмель–суша. Сначала допустима загрузка существующей кэшированной подложки как текстуры для проверки камеры; затем заменить её картами данных и GPU-процедурами. Сохранить стабильные координаты текстур в единицах мира.

Перенести форму чашки, тень, стенки, перегородки и границы. Проверить детали при приближении: физическая сетка не обязана задавать разрешение художественного рисунка. Выбрать mipmaps/уровни детализации для цветных текстур; маски непроходимости не усреднять как цвет.

**Приёмка:** узнаваемая текущая палитра и берег без швов, мерцания и растяжения при панорамировании. Изменение грунта/залежей появляется без полной пересборки кадра на CPU. Рамка и непроходимые области совпадают с физикой.

## Этап 3. Общая карта среды, минерал и свет

**Работа:** подключить числовые поля, сглаживание плотности только для показа и формулы прозрачности. Заменить CPU-сборку `ImageData` для мутности и минерала GPU-проходами. Сохранить световые пятна, их перекрытие без искусственного суммирования, ослабление света минералом и размытие края.

Подготовку данных выполнять до светового прохода того же кадра, чтобы свет не использовал устаревшую мутность. Ограничить разрешение мягких эффектов отдельно от чёткого изображения местности и подписей. Один маленький проход размытия использовать только там, где он нужен, не размывать целиком финальную сцену.

**Приёмка:** одинаковая физическая плотность даёт согласованные цвет и прозрачность; узкие перегородки не пропускают мутность. Рассвет, яркое солнце и слабый свет читаются как прежде. При остановке мира карты не загружаются непрерывно без причины.

## Этап 4. Рябь внутри общего GPU-рендера

**Работа:** перенести существующий `WaterFlowShader` на WebGL2 и в общий контекст. Удалить копирование его холста в Canvas 2D и отдельную CPU-маску воды. Воспроизвести нынешнее фазовое смешивание, масштабы и зависимость от физической скорости.

Передавать физическую скорость в абсолютных мм/с. Не нормализовать визуальную скорость каждого потока отдельно: более быстрые потоки должны двигаться быстрее. Не добавлять отдельный радиальный толчок вулкана, если он уже присутствует в `flowAt`. Сохранить достаточную точность слабых потоков рядом с сильными источниками.

**Приёмка:** вода не выглядит слоем над сушей, рисунок связан с мировой поверхностью; скорость и направление соответствуют полю. Первое извержение и слабое течение видны одновременно. Режим «Процессы» показывает то же физическое поле. Прежний отдельный контекст WebGL1 больше не нужен.

**Контрольная точка:** после этапов 1–4 уже можно оценить единый рендер поверхности и среды. Сравнить качество и время кадра до переноса остальных эффектов.

## Этап 5. Источники, минерал и динамические детали

**Работа:** перенести все стадии вулканов, отверстия, ободки, подготовку, залпы, истечение, вспышки, воронки, искры, пену и блики. Фигуры рисовать треугольниками/экземплярами прямоугольников с аналитическим краем; не полагаться на широкие аппаратные линии и предел размера точек.

Частицы сначала оставить на CPU с прежними правилами движения и передавать одним буфером экземпляров. Перенос вычисления частиц на GPU рассматривать отдельно по результатам профилирования. Задать верхние пределы числа частиц и служебных массивов, применять текущую зависимость деталей от масштаба.

Определить порядок слоёв: местность → среда и её свет → частицы/выбросы → отверстия и ободки → диагностика → стенки и подписи. Уточнить отдельные исключения по эталонным кадрам; не терять видимость жерл под рябью.

**Приёмка:** источник узнаваем во всех стадиях и масштабах, нет скачка эффекта после загрузки и двойного проигрывания старых залпов. Частицы маскируются границами мира. Число GPU-команд зависит от групп эффектов, а не линейно от каждой частицы.

## Этап 6. Диагностика, линейки и миникарта

**Работа:** перенести стрелки/цвет обменов режима «Процессы», пробу, координатную сетку и подписи. Для подписей — кэшируемый атлас текста; пересборка при изменении необходимых подписей или масштаба плотности пикселей, без рисования текста заново каждый кадр. Сохранить доступные DOM-подписи и существующие обработчики ввода.

Миникарту рендерить той же логикой из отдельной камеры. Предпочтительный вариант — цель в том же контексте и вывод в отдельный холст через `ImageBitmap`, если это не очищает основной кадр и не даёт дорогую передачу; проверить путь отдельно. Если он неудобен, использовать второй небольшой контекст WebGL2 с теми же программами и общим CPU-состоянием, обновляемый только при необходимости. GPU-текстуры между контекстами не общие. Финальный выбор зафиксировать после измерения; не использовать синхронный `readPixels` для постоянного вывода миникарты.

**Приёмка:** миникарта показывает весь мир и окно камеры, правильно навигирует после изменения размера чашки. Линейки чёткие на DPR 1/2, единицы прежние. Процессы, проба, перетаскивание миникарты и компоновка панели работают без изменений смысла.

## Этап 7. Профилирование и полное переключение

**Работа:** повторить матрицу этапа 0 минимум тремя прогонами с прогревом и чередованием вариантов. Выделить загрузку числовых карт, CPU-подготовку и GPU-работу. GPU-время измерять асинхронными timer queries при наличии соответствующего расширения, отбрасывая disjoint-результаты; при его отсутствии явно указать, что GPU-время не измерено.

Предварительные ориентиры на выбранном устройстве: устойчивые 60 FPS в стандартной сцене; p95 интервала кадра до 20 мс; p95 CPU-подготовки и отправки кадра до 8 мс; отсутствие регулярных задач рендера главного потока дольше 50 мс. Это цели проверки, не обещание для любого устройства. На тяжёлых сценах время кадра не должно ухудшиться более чем на 10% относительно базы без отдельного объяснения и измеримого выигрыша в качестве.

Считать память по выделенным текстурам/буферам, а не выдавать её за измеренную общую VRAM. Разрешение полноэкранных целей связывать с бюджетом памяти; мягкие эффекты оставить ограниченными. Не добавлять отдельный упрощённый режим: ограничения ресурсов относятся к одному WebGL2-рендеру.

Удалить старую Canvas-сборку, пути автоматического fallback, неиспользуемые кэши плиток и старый `WaterFlowShader`. Проверить `flow-markers.ts` и другие остатки прежних экспериментов на отсутствие потребителей перед удалением. Однократные генераторы атласов при необходимости сохранить.

**Приёмка:** приложение использует только новый рендер чашки, нет скрытого перехода на Canvas. `npm run build`, существующие проверки физики и воспроизводимости проходят. Отчёт содержит результаты, кадры, ограничения и список удалённых временных решений. Спецификация мира отражает фактическую архитектуру.

## Проверки, которые нужны при реализации

- Физика: совпадение хешей на фиксированных шагах до/после смены рендера; продолжение сохранения; сохранение массы. Рендерер не изменяет массивы мира и не вызывает дополнительное продвижение симуляции.
- Координаты: центр, края круга/прямоугольника, масштаб около указателя, изменение размеров, переход CSS↔DPR↔мм.
- Сцены: вода, отмель, суша, узкий проход, закрытая перегородка, сильный и слабый поток рядом, первое извержение, воронка, изменение грунта.
- Управление: пауза/пуск, ×1/×10/высокое ускорение, загрузка, новый сид, миникарта, линейки, процессы, проба, скрытие вкладки и возврат без скачка накопленного эффекта.
- Ресурсы: многократная смена мира и размеров, принудительная потеря/восстановление контекста, ошибка компиляции, отсутствие WebGL2. Проверить освобождение текстур и буферов, отсутствие роста при повторении одинакового цикла.

Автоматизировать значимые числовые проверки и координатные преобразования. Художественные решения проверять на фиксированных кадрах и в движении; не требовать побитового совпадения изображений разных GPU. Не создавать тесты, которые просто повторяют формулы реализации.

## Последующее улучшение картинки

После завершения миграции отдельно оценить накопительное движение ряби через две чередующиеся GPU-цели, взаимодействие рисунка с препятствиями, читаемость силы потоков и более согласованное освещение выбросов. Такой накопитель хранит только визуальный рисунок: масса и скорость по-прежнему задаются физикой. Для долгого ускоренного прогона нужны ограничение шага переноса, обновление рисунка и сброс после скачка времени.

Эти улучшения не являются условием завершения переноса. Они не заменяют физическое течение декоративной симуляцией и не включают изменение длительности извержения.

## Порядок поставки и завершение

Поставлять отдельными проверяемыми изменениями: база сравнения → устройство/камера → местность → среда/свет → рябь → источники → интерфейсные обозначения/миникарта → удаление старого рендера. После каждого этапа сохранять рабочий предварительный просмотр и короткий отчёт. Коммиты создавать по запросу пользователя. Сроки оценить после этапов 0–1: наиболее неопределённы точное воспроизведение процедурной местности, смешивание слоёв и вывод миникарты.

Переход завершён, когда вся чашка и миникарта рисуются в WebGL2, текущие функции сохранены, физика даёт те же результаты, ресурсы восстанавливаются после потери контекста, старый рендер удалён, а производительность подтверждена сравнением.
